Testing hash functions

A hash function is supposed to behave like a random function of its input: flip one input bit and the output should be freshly random. That claim is testable with the same machinery as the PRNG suites — plus a family of criteria of its own — and its limits are sharper here than anywhere else, because hash functions face adversaries, and adversaries don't sample from distributions.

The avalanche effect and the Strict Avalanche Criterion

The design goal goes back to Feistel: a small input change should "avalanche" into a large, unpredictable output change [Feistel 1973]. Webster and Tavares made it precise as the Strict Avalanche Criterion: complementing any single input bit should flip each output bit with probability exactly ½ [Webster & Tavares 1985].

The measurement is direct. For input bit i and output bit j, draw T random inputs x, compute f(x) ⊕ f(x ⊕ ei), and record the fraction p̂ij of trials in which bit j flipped. The result is the avalanche matrix; under the null hypothesis each cell's flip count is Binomial(T, ½), so cells convert to z-scores or the whole matrix to a chi-square statistic, and "worst cell bias |2p̂−1|" becomes the headline number — SMHasher fails a hash whose worst bias exceeds about 1% [Castro et al. 2005] [Appleby].

Bit independence

SAC is necessary, not sufficient: every output bit can flip with probability ½ while pairs of output bits flip together. The Bit Independence Criterion, from the same Webster–Tavares paper, demands that for any flipped input bit, every pair of output bits change independently — measured by correlating the avalanche indicator variables over the sample, or chi-square on the 2×2 table of joint outcomes (00/01/10/11 each ¼). SAC plus BIC says the avalanche variables behave like independent fair coins — the local signature of a random function [Webster & Tavares 1985].

Collision statistics and the birthday bound

Hash n distinct keys into 2b buckets and, if the hash behaves randomly, the expected number of colliding pairs is

E[C] = n(n−1) / 2b+1

with the count approximately Poisson for small expectations. Collision probability reaches ½ near n ≈ 1.18·2b/2 — the birthday bound that gives b-bit hashes only b/2 bits of collision resistance. Test suites score keysets by observed-vs-expected collisions in both directions: too many collisions means clustering; too few, in truncated-output tests, means structure. Distribution tests do the same for bucket occupancy via chi-square. These are the collision and equidistribution tests wearing hash-function clothes.

SMHasher and its descendants

Austin Appleby's SMHasher (~2010) did for non-cryptographic hashes what Diehard did for generators: packaged the embarrassing questions. Its structure survives through Reini Urban's much-extended fork and Frank J. T. Wojcik's SMHasher3 rewrite [Appleby] [Urban] [Wojcik].

Hash-as-PRNGFeed hash output into stream tests (below)
SpeedBulk throughput and small-key latency — not a quality test but the reason most of these hashes exist

The structured keysets are the insight. Random keys are the easy case — almost anything looks fine on them. Real workloads hash counters, pointers, coordinates, and near-identical strings, so the battery deliberately feeds the hash minimal-entropy, maximal-structure inputs where weak mixing has nowhere to hide. SMHasher3 added the statistical rigor the original lacked: every result becomes a p-value corrected for the ≈16,000 tests in a full run, so a reported failure is meant to be a real one [Wojcik].

Hash as PRNG: borrowing the stream suites

Define G(k) = H(k‖0), H(k‖1), H(k‖2), … and any hash becomes a counter-mode generator whose stream can be piped into Dieharder, PractRand or BigCrush. The input is the adversarially boring one — a counter, differing in a handful of low bits per step — so stream failures indict the hash's mixing directly. This construction is how GPU-oriented hashes were ranked by BigCrush failure count [Jarzynski & Olano 2020], and it is the design principle, run in reverse, of the counter-based generators (Philox, Threefry) that now dominate parallel simulation: a good keyed mixer of a counter is a good PRNG [Salmon et al. 2011]. xxHash's XXH3, BLAKE3 and SipHash all pass these batteries; for cryptographic hashes that is table stakes rather than news [Collet].

Statistical testing in the SHA-3 competition

NIST's competitions institutionalised a version of this. For AES, NIST itself ran candidate ciphers' outputs — avalanche datasets, low- and high-density inputs, plaintext/ciphertext correlation streams — through the STS battery [Soto & Bassham 2000]. For SHA-3, the heavy statistical lifting came from the research community: round-reduced candidates were tested for how many rounds it takes before outputs become statistically indistinguishable from random, turning the battery into a security-margin ruler [Doğanaksoy et al. 2010], with companion methodology for applying randomness tests to sequences as short as a hash output [Sulak et al. 2010]. NIST's official round reports weighed that evidence alongside what actually decided the competition: cryptanalysis, security margins, and performance [NIST IR 7896].

The hard lesson: statistical quality is not security

Every test on this page measures average-case behaviour over sampled inputs. An adversary is not a sampling distribution.

The demonstration came in two acts. At 28C3 (2011), Klink and Wälde showed that the multiplicative string hashes inside PHP, Java, Python, Ruby and ASP.NET admit cheap multicollisions — kilobytes of crafted POST parameters drove web servers into quadratic hash-table behaviour and denial of service [Klink & Wälde 2011]. Vendors responded with randomized seeding, and MurmurHash — a hash with an excellent SMHasher record — became the recommended fix. Act two: Aumasson, Bernstein and Boßlet produced seed-independent collisions for MurmurHash2, MurmurHash3 and CityHash64 — inputs that collide for every seed, by inverting the very mixing rounds whose statistical behaviour was flawless. The attack exploits invertibility, a structural property no black-box statistical test can see [Aumasson & Bernstein 2012] [Boßlet 2012]. Their constructive answer, SipHash, is a keyed PRF with an actual security argument, since adopted as the hash-table hash of Python, Ruby, Rust and others [Aumasson & Bernstein 2012].

The formal frame. Every statistical test is a distinguisher: an algorithm trying to tell H's outputs from a random oracle's. Cryptographic security claims quantify over all efficient distinguishers — including ones that know the algorithm and choose inputs adaptively. A battery checks a few dozen fixed, cheap, non-adaptive ones [Kaminsky 2019]. That is why failing a battery is damning while passing one proves little, and why NIST's SHA-3-derived standards state their guarantees in indistinguishability terms rather than as test results [NIST SP 800-185]. It is the foundations-page asymmetry, with an adversary attached.
